# 工程案例

## 案例一：交还 AI 提示成功，但顾客收不到回复

### 现象与排查

员工点击交还 AI 后页面显示成功，顾客继续发送消息却没有收到回答。按“回调 → 入站 → 模型 → 出站 → 平台结果”的链路检查，发现模型已生成回答，真正失败发生在平台发送阶段。

### 根因

本地会话所有权已恢复 AI，但旧实现把平台状态转换拒绝误当成会话已结束。平台仍可能处于不允许发送的接待状态，造成两个系统不一致。

### 修复

1. 先验证任务是否仍可执行、当前是否人工所有、摘要是否完整。
2. 尝试切回智能接待；转换被拒绝后查询平台真实状态。
3. 若仍是人工接待，按支持的流程结束并查询确认；已结束的会话等待顾客下一条新消息。
4. 查询或结束失败时保留人工状态，不显示假成功；不重发历史消息。
5. 回归覆盖重复点击、旧任务、查询失败、结束失败和平台未实际改变状态。

核心实现：[交接服务](../src/service_agent/application/staff_appointments.py)、[平台适配器](../src/service_agent/infrastructure/wecom_api.py)。回归入口：[状态不一致测试](../tests/test_handoff_return_regression.py)。

这体现的是外部系统状态协调与失败关闭，不是对所有平台和所有会话条件的通用保证。公开测试使用模拟平台，不等于真实端到端验收。

## 案例二：模型承诺发送不支持的定位

模型曾用“稍后发定位”代替完整文字地址，还夹带无关预约承诺。系统并没有定位卡片动作，生成这句话也不会让平台获得该能力。

完整项目的修复是补充核实过的文字地址知识，增加回复校验，发现不支持的承诺时要求模型修复，并验证地址完整性。公开节选不发布商家地址、完整业务知识或这部分生产提示词，只演示相同的 Markdown 检索机制。

经验是：工具能力必须与模型承诺一致，不能让流畅话术替代真实执行结果。

## 面试讨论方向

- 如何区分模型错误、消息管线错误与平台拒绝？
- 为什么先停止 AI，再通知员工？
- 重试和幂等分别解决什么问题，哪些场景需要对账？
- 为什么不用一句提示词代替状态机和权限校验？
- SQLite 与词项检索在什么规模下需要重新评估？
