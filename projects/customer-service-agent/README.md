# Forthatday 企业微信智能客服

面向婚纱工作室的业务型客服 Agent：将顾客咨询、款式推荐、试纱预约、付款截图辅助处理与员工协同串联起来，服务于顾客首次到店前的接待流程。

本目录展示 `agent_v2` 原项目，保留 `forthatday_agent` 包名和原版业务源码，不是重新命名的示例系统。私密运行数据不随源码公开。

## 应用场景

Forthatday Studio 是小型婚纱工作室。顾客通常先在微信询问款式、试纱费用、门店位置和时间，店员还需要维护商品、确认档期、核对付款及处理特殊需求。

项目让 AI 承担常规咨询与信息收集，把必须由店员决定的事项保留给人处理。目标不是让模型完全自主经营门店，而是建立“顾客咨询 → AI 接待 → 店员确认 → 预约落地 → 必要时人工处理”的工作流。

适用阶段是首次到店前；试纱后的寄送、租赁履约和售后仍由店员处理。

## 能做的功能

### 顾客咨询与推荐

| 功能 | 实际行为与边界 |
| --- | --- |
| 自动咨询回复 | 基于企业知识回答试纱流程、公开价位、门店地址和预约规则，结合会话历史继续沟通 |
| 偏好与上下文记忆 | 保存顾客明确表达的需求、风格和意向，不能伪造店员确认的事实 |
| Markdown 知识检索 | 按标题分块，通过词项及标题权重检索，将相关内容交给模型 |
| 款式推荐与发图 | 根据已核实商品目录和风格标签匹配，每轮最多推荐三个不同款式并创建图片发送任务 |
| 不确定事项转人工 | 对无法确认的图片身份、库存尺码、特殊价格、退款和例外政策请求店员协助，不编造结果 |

### 预约与付款截图处理

| 功能 | 实际行为与边界 |
| --- | --- |
| 预约信息收集 | 收集意向时间、姓名和联系电话，不在店员确认前承诺档期 |
| 店员确认时间 | 在企业微信通知员工，通过签名任务链接批准或拒绝时间 |
| 付款码发送 | 只有时间获批后才发送私有配置中的微信、支付宝付款码，防止重复发送 |
| OCR 凭证识别 | 使用 RapidOCR 提取截图中的金额、收款方和支付状态，结合置信度按规则判断 |
| 预约确认 | 时间已获批且付款证据符合已配置规则时确认预约；模糊或不匹配证据交员工复核 |
| 改期、取消与迟到 | 创建员工处理任务；未确认新时间前保留原预约，不由模型擅自退款或释放档期 |

**付款截图识别不等于银行到账核验。** 当前流程依据商家接受的截图证据规则工作，没有支付平台到账回调或商户查单能力。

### 员工协同与管理后台

| 功能 | 实际行为与边界 |
| --- | --- |
| 企业微信员工反馈 | 发送时间确认、付款复核、人工接管等通知，记录员工决定 |
| 人工接管与交还 AI | 使用 `ai`、`human_pending`、`human` 所有权；人工期间禁止 AI 自动回复，交还时摘要必填并协调平台真实状态 |
| 客户上下文查看 | 员工查看系统保存的消息、摘要、预约和付款状态；原生窗口不伪造或重放顾客历史气泡 |
| 商品与实体件管理 | 管理款式、图片引用、不同实体件、尺码、位置、状态和实物流转 |
| 预约日历与冲突检查 | 查看月度预约、手工录入预约、关联心仪款式和实体件档期，提示冲突 |
| 使用分析与库存规划 | 汇总款式需求、推荐和使用情况，辅助员工维护库存 |
| 官网预约申请 | 接收网站表单，持久化并在后台标记待联系、已联系或已结束；不会自动确认预约、收款或发送微信消息 |

库存、尺码和目标日期可用性遵循“平台核验 + 店员确认”，推荐某款不代表一定有货或该日期一定可试。

## 一条典型业务流程

1. 顾客在微信客服询问试纱费用或风格，AI 检索知识后回答。
2. 顾客表达偏好，系统从已核实商品目录中推荐款式并发送主图。
3. 顾客提出到店时间，AI 收集预约信息，创建员工确认任务。
4. 店员批准时间后，系统发送付款说明和付款码。
5. 顾客提交截图，OCR 和规则引擎评估；符合条件则确认预约，不确定则转人工复核。
6. 顾客提出改期、退款或特殊需求时，交给店员处理；人工接管期间 AI 保持静默。
7. 员工填写摘要并完成平台状态协调后，顾客下一条新消息可继续由 AI 接待，不补发历史回复。

这是功能流程说明，不表示每一个分支都已在最近一轮真实客户会话中重新验收。

## 技术实现

Python 3.12、标准库 HTTP 服务、DeepSeek 兼容接口、SQLite WAL、Markdown 检索、RapidOCR / ONNX Runtime、企业微信加密回调与客服 API、Docker Compose、Caddy HTTPS。

模型返回结构化 JSON 决策，应用代码校验回复、动作和业务状态后再执行。回调只负责验证与任务持久化，消息同步、模型、OCR 和发送由后台处理，并保留去重、重试、恢复和审计记录。

| 目录 | 内容 |
| --- | --- |
| [src/forthatday_agent/domain](src/forthatday_agent/domain/) | 会话、消息、预约、记忆和动作模型 |
| [src/forthatday_agent/application](src/forthatday_agent/application/) | 对话引擎、动作校验与执行、员工后台、库存界面和官网申请 |
| [src/forthatday_agent/infrastructure](src/forthatday_agent/infrastructure/) | 模型、企业微信、SQLite、OCR、知识与商品检索 |
| [knowledge](knowledge/) | 允许公开的原版业务知识；内部品牌文件未发布 |
| [tests](tests/) | 原项目回归测试，使用隔离数据和模拟外部接口 |
| [scripts](scripts/) | 原版启动、导入、诊断和历史维护脚本 |

## 测试与真实运行

Python 3.12 环境下执行：

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

真实运行需复制 `.env.example` 为本地 `.env`，配置自己的模型 Key、企业微信授权与回调参数、员工账号、HTTPS 地址和签名密钥，同时准备私有付款码、付款核验规则与商品目录，再运行：

```bash
python scripts/run_wecom_service.py
```

回调路径为 `/wecom/callback`，健康检查为 `/healthz`。不配置业务私有文件不能直接完成生产流程；不要把配置模板里的域名当成自己的授权入口。

Docker 文件和部署脚本保留原版，适合作为结构参考。历史部署脚本不是对现网拓扑的最新自动发布方案；维护、恢复和重排任务脚本可能写数据库或触发消息，运行前必须审查、备份并改成自己的环境，不能直接对现网执行。

## 当前限制

- 知识检索是文字与标签匹配，没有上线 Embedding、向量数据库或图片向量检索。
- OCR 不是到账证明，不支持模型自主退款或修改支付状态。
- 不支持通过现有业务动作发送定位卡片；位置问题直接回复完整文字地址。
- 不宣称严格 exactly-once、高并发验证或未经统计的效果提升。
- 私有数据、商品图片与品牌清单未公开；测试中的一处私人联系方式换成示例，业务源码未改名或简化。
